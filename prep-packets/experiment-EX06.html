Seventy-two-hour local task and recovery drill

Can a benign application continue its assigned work and can another operator recover it using a written procedure?

Define the test before you start

Operator task: Run a one-record-per-minute local logger for 72 elapsed hours; recover from predeclared ordinary service restart, network interruption and normal device reboot.

Success rule: Account for the expected 4,320 scheduled records, identifying missing/late records and planned downtime separately. Each recovery test returns the task to service under a predeclared target without losing the baseline image.

Materials

  • Owned/permissioned device and spare cloned storage containing dummy data.
  • A safe private test network and a laptop observer; nothing connected to industrial equipment.
  • A simple logger producing timestamped sequence numbers, plus a runbook.

3–4 active hours plus 72 elapsed hours; second operator 15–20 minutes. No destructive fault injection performed.

Repeatable procedure

Step 1

DoFreeze versions/configuration and save a known-good spare image. Define timestamp source, record interval and recovery target before the run.
RecordConfiguration; image ID; planned schedule; clock synchronisation method.

Step 2

DoRun the logger with a sequential record counter; the observer checks health at a declared interval, recording its own outages. Record temperatures with the documented Pi tool at a modest fixed interval if supported.
RecordRecord number/time; application health; observer health; temperature samples.

Step 3

DoAt predeclared times restart only the test application, disconnect/reconnect the test network, then perform a normal shutdown/reboot. Keep each event isolated.
RecordEvent start; local task impact; remote visibility loss; recovery finish; intervention.

Step 4

DoOn a cloned card only, attempt the normal supported update path and verify the same task; return to the baseline image if needed.
RecordBefore/after versions; active time; verification; rollback result.

Step 5

DoHave a consenting second operator use the runbook for one ordinary recovery drill without coaching.
RecordStep/intervention log; physical-access requirement; result.

Step 6

DoReconcile expected records with actual records and event log. Classify cause as supported or unknown; do not assign a hardware cause from a symptom alone.
RecordMissing/late/duplicate counts; planned/unplanned distinction; cause confidence.

Controls, stopping rules and limits

Hold these conditions fixed

  • Keep observer failure separate from device/application failure.
  • No abrupt power-cut test in the baseline; normal shutdown only.
  • Do not change cooling, application or network configuration mid-run without starting a new labelled segment.
  • Define the 4,320 scheduled record times as minute 1 through minute 4,320 after the start; do not add a time-zero record to that denominator.

Stop when

  • Stop if the test affects another person’s work or a real-world control process.
  • Use no private production dataset, load or network.

What this cannot establish

  • Seventy-two hours is not evidence of multi-year field reliability.
  • A missed remote health check may reflect the network or observer, not the device.
