CM5 prototype-to-production gate and provisioning trial

Which steps remain after a module boots, and how much operator work does a repeatable provisioning procedure involve?

Define the test before you start

Operator task: Desk path: produce a gate list covering interfaces, enclosure, compliance, image creation, provisioning, verification and field recovery. Physical path, only if equipment is available: install the same nonconfidential OS-only image three times and prove each resulting device boots the chosen task.

Success rule: Every gate has an owner and source or an explicit unknown. Optional physical runs each reach a verified boot/application response; fixture completion alone does not pass.

Materials

  • Requirements sheet for a read-only local sensor/logger or kiosk; no safety-critical controller.
  • Desk-only path: module and product documentation.
  • Optional physical path: permissioned CM5, correct I/O board or an independently available Programming Jig, compatible supply and spare storage; no $600 fixture purchase assumed.

3–5 hours desk work plus two 20 minute reviews; optional physical setup 1–2 hours and three timed runs. Borrowed equipment only unless user independently chooses otherwise.

Repeatable procedure

Step 1

DoDraw the finished-system requirements and assign responsibility to module supplier, integrator and operator. Record required product certificates and their exact scope.
RecordGate; source/version; owner; evidence still needed.

Step 2

DoHave two independent engineers review the same list; retain disagreements and the basis each cites.
RecordP02/P07 contact role; changed gate; unresolved conflict.

Step 3

DoIf hardware is available, freeze exact module, image hash and uncompressed size, interface/network, software versions and OS-only provisioning mode. Use a spare module/image with owner permission.
RecordConfiguration ID and availability; desk-only if absent.

Step 4

DoFor three repetitions, time handling/setup, automatic write, and boot/application verification separately. One run is a repeat on the same device unless three devices are actually available; identify which.
RecordHandling seconds; write seconds; verify seconds; run/device ID; success/failure.

Step 5

DoIf both carrier and jig paths are genuinely available, run the same image and verification on both; label unmatched network or storage configurations. Otherwise leave the comparison unperformed.
RecordPaired runs or no-comparison reason; image conditions.

Step 6

DoPrepare a synthetic example manufacturing record with field names only; never request a partner’s production database or keys.
RecordImage identifier; timestamp; result; anonymised demo device ID; evidence boundary.

Controls, stopping rules and limits

Hold these conditions fixed

  • Baseline uses OS-only mode. Secure-boot key programming can be permanent and is excluded from this trial.
  • Do not remove a module while programming or press undocumented controls.
  • Do not compare timing with the documentation example unless image size, mode and relevant connection conditions match.

Stop when

  • No fixture or permission: complete the desk gate sheet and mark hardware measurements not performed.
  • If flashing fails, follow official troubleshooting; do not repeatedly force removals or change permanent security settings.

What this cannot establish

  • Three repeated writes are not manufacturing throughput, production yield or a cost quote.
  • A compliance checklist does not certify a finished product.
