Opening questions and follow-up branches

1. Can a user determine from public material which team owns this issue: Imager, OS, kernel, application or accessory?

If yesWhich repository, release tag and minimal reproduction would let a maintainer act without another information round trip?
If noWhere should the user start, and how does a correct hand-off become visible?
If vagueHere are my exact versions and three reproduction steps. Which one observation would most quickly separate the possible causes?
Public evidencePublic contribution guidance, issue template, linked fix and release notes.
PurposeRouting friction is observable; a generic assertion that community support is strong is not.
Your queue

2. Does an image that boots successfully also demonstrate that a second operator can provision and recover the device consistently?

If yesWhat documented verification step confirms configuration, application health and recovery rather than only a green completion indicator?
If noWhich separate tests should I add to the runbook, and which are appropriate on a spare device?
If vagueWould you sign off my success rule: correct image identifier, expected application response, and successful normal reboot? What is missing?
Public evidenceAn existing public deployment checklist or synthetic example log; no production serials, keys or manufacturing database.
PurposeA working prototype and a repeatable operational procedure are separate observations.
Your queue

3. Is the period of OS or driver support for my exact product and image expressed in a public commitment?

If yesPlease link the statement and specify its product, software branch, coverage and date; does it include the particular peripheral?
If noWhich public signals should a user follow, and which maintenance responsibility remains their own?
If vagueDistinguish hardware production lifetime, availability of source code and a promised support term; identify which one the source actually commits to.
Public evidencePublic support policy, release history and source repository, with caveats retained.
PurposeA long production lifetime is not automatically a software service-level commitment.
Your queue

What to ask to see—and what this person cannot establish

Evidence requests

  • Versioned minimal reproduction stripped of credentials and personal information.
  • Public report → diagnosis → fix → release → user-verification chain.
  • A runbook another consenting person can follow, with actual timed results entered only after testing.

Limits of this contact

  • A public contributor may not be a Pi employee and cannot speak for company resource allocation.
  • One fixed issue does not estimate overall defect frequency or response-time performance.
  • A software maintainer may not know manufacturer yield, gross margin or confidential customer deployments.

Earn the next conversation

Contact 1Offer a precise real reproduction and explain the research purpose; use support for the technical problem and request any interview separately.
Next-contact trigger: Only after searching the existing public issue history.
Contact 2Test the proposed public fix, return the version/configuration and unsuccessful attempts as well as successes.
Next-contact trigger: After a substantive technical reply; no duplicate ticket.
Contact 3Offer an accurate documentation clarification or report that the fix reached an ordinary user; request review only if useful to the maintainer.
Next-contact trigger: When a released fix or new test result adds information.

Recruit a balanced sample

Use one Pi engineer and one independent contributor or user of the same component. Record employment or volunteer status as self-described; do not infer it from a forum badge. Include an unresolved or unsuccessfully reproduced case in the issue ledger.
