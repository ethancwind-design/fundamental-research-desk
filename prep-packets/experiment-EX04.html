Same useful workload: system cost, latency and energy

For one declared task, what does each available platform require to meet the same quality and responsiveness rule?

Define the test before you start

Operator task: Baseline: run EX01’s offline catalogue display, complete a scripted set of 30 actions and perform a normal restart. Optional AI track: use one fixed small model file/quantisation and a ten-item synthetic extraction task with predetermined correct answers on both platforms.

Success rule: Set acceptance before setup: baseline returns the expected status for all 30 actions; optional AI meets the researcher’s declared exact-field scoring threshold. A platform that does not pass stays in the results as failed; do not compare speed alone.

Materials

  • One owned/borrowed Pi and one genuinely available alternative capable of the same job; source that alternative’s official documentation before testing.
  • Same display resolution, local dataset and comparable storage/network where possible.
  • A plug-in power meter with its model, resolution and logging interval recorded. If none is available, leave energy unmeasured.

1–2 active days; three short idle/load blocks per configuration plus setup. No alternative hardware or power meter purchased; use a narrower timing-only study if equipment is unavailable.

Repeatable procedure

Step 1

DoFreeze task, quality rule, model/data hashes if applicable, versions, peripherals, cooling and complete BOM. Separate actual delivered spending from equipment already owned.
RecordPredeclared protocol ID; full configuration; borrowed/owned/quoted status.

Step 2

DoRandomise platform order if two operators participate; each gets one declared practice run. Record setup active time separately from unattended downloads.
RecordOperator/experience; order; setup phases and assistance.

Step 3

DoAfter a ten-minute settling period, measure three ten-minute idle intervals and three ten-minute task intervals, alternating platform order. Use the same AC-meter boundary including its own supply, with display power separately included or excluded for both.
RecordStart/end watt-hours or logged watts; duration; ambient conditions; load state; meter limits.

Step 4

DoCollect 30 warm task latencies per platform with the same start/end definition; separately record three cold-start or first-load attempts. Use a screen recording only of your own dummy task if manual timing is inadequate.
RecordAll raw durations; unsuccessful responses; median and range; no precise tail claim from 30 samples.

Step 5

DoIf using AI, freeze prompt text, token/output limit and deterministic settings where supported; distinguish model loading, first-token and full-response time, and score each answer before timing comparison.
RecordQuality for each input; cold/warm state; model/runtime; network role.

Step 6

DoRepeat one baseline run after a normal restart; retain unsupported peripherals or missing software as outcomes, not excluded trials.
RecordRecovery time; run exclusions with reason; exact constraint.

Controls, stopping rules and limits

Hold these conditions fixed

  • No overclocking or undocumented tweaks in the baseline; any later tuned run gets a separate configuration ID.
  • Do not replace a Linux SBC with a microcontroller for a task requiring Linux. A Pico-versus-other-MCU task is a separate experiment.
  • Meter precision must support the claimed difference; retain totals and time if instant power is noisy.
  • Do not calculate company margin, market demand or population performance from this task.

Stop when

  • Do not bypass permissions or connect experimental hardware to a plant network.
  • Stop on unstable power or an unsafe physical setup; record the failed configuration.

What this cannot establish

  • This answers one task with specific versions and skills.
  • Unmatched architectures, model kernels, cooling and storage are recorded differences, not hidden controls.
  • Nameplate watts and software-reported CPU power are not substitutes for whole-system AC energy.
