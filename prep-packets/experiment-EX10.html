Trace a specific public bug from report to usable release

What separates a reported usability problem, a merged fix and a fix an ordinary user can actually obtain?

Define the test before you start

Operator task: First complete the public chronology. If a matching disposable environment is available, test only whether a custom image can be selected by its complete path, stopping before any storage write.

Success rule: A chronology records report, proposal, merge and release separately. Optional reproduction records before/after file-selection behaviour in the declared environment, including an unsuccessful reproduction.

Materials

  • The three public URLs; a timeline sheet.
  • Optional matching permissioned Linux/KDE environment, official old/new Imager packages and one harmless local image file; no SD-card writing is needed for the file-dialog test.

45–60 minute chronology; optional 1–2 hour controlled UI comparison. No packages installed and no issue posted by the assistant.

Repeatable procedure

Step 1

DoRecord source dates and versions from the issue, PR and release; distinguish authored, merged and released dates.
Record3 February report; 3 March merge; 26 March release; URLs and locators.

Step 2

DoRead the issue’s exact symptom and environment and the narrower PR change. Keep file listing behaviour and typed-path acceptance distinct.
RecordSymptom A/B; environment; what the fix claims to address.

Step 3

DoIf suitable Linux/KDE equipment is not available, stop at trace-only and mark reproduction not performed. Otherwise use a disposable test profile and official package sources; do not downgrade the user’s everyday installation.
RecordEnvironment match; package source/version; eligibility for physical comparison.

Step 4

DoAttempt the documented custom-image selection using a complete path to a harmless image file on old and fixed versions; three attempts each after an app restart. Stop before selecting or writing a destination drive.
RecordAttempt; version; path-selection result; screenshot with private paths redacted.

Step 5

DoRecord what an ordinary user would have to find and install to receive the fix, and whether the current supported release behaves as expected. Do not seek an interview unless a genuine unresolved question remains.
RecordRelease discoverability; package availability; actual confirmation or missing evidence.

Controls, stopping rules and limits

Hold these conditions fixed

  • A merge does not prove the reporter’s issue is resolved in every environment.
  • Do not treat the contributor’s handle as proof of Pi employment.
  • Keep this ordinary UI issue separate from security testing and from the Mac release-asset correction.

Stop when

  • No matching safe environment: chronology only.
  • No drive write, private credential entry or execution of code from unknown attachments.

What this cannot establish

  • One selected closed issue is not a defect-frequency or engineering-productivity score.
  • The public record may not include a reporter’s confirmation even where the release contains the fix.
